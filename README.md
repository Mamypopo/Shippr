# Shippr

ระบบติดตามตลาดค่าระวางเรือและเลือกสายเรือด้วย AHP สำหรับ freight forwarder

สามอย่างที่ระบบนี้ทำ

1. **ติดตามค่าระวาง** — Drewry WCI, SCFI รายสัปดาห์ และสัญญาณตลาดรายวัน (BDRY, น้ำมันดิบ WTI/Brent, หุ้น ZIM) พร้อม WoW, MoM, ค่าเฉลี่ยเคลื่อนที่, การเตือนเมื่อราคาพุ่ง และแปลงเป็นบาทให้อัตโนมัติ — ดูคำอธิบายแต่ละตัวได้ที่ [ดัชนีและข้อมูลตลาดแต่ละตัวคืออะไร](#ดัชนีและข้อมูลตลาดแต่ละตัวคืออะไร)
2. **เฝ้าระวังการติดขัด** — เวลารอเทียบท่าของท่าเรือ hub และข่าว disruption ที่ติด tag อัตโนมัติ (ทะเลแดง การประท้วง จุดคอขวด)
3. **ตัดสินใจเลือกสายเรือ** — Analytic Hierarchy Process เต็มรูปแบบ พร้อม decision memo ที่พิมพ์ส่งลูกค้าได้

## ดัชนีและข้อมูลตลาดแต่ละตัวคืออะไร

ส่วนนี้เขียนไว้สำหรับคนที่ต้องใช้งานจริง ไม่ใช่คนเขียนโค้ด — ถ้ากรอกข้อมูลในหน้า
"กรอกข้อมูลตลาด" แล้วไม่แน่ใจว่าตัวเลขที่เห็นควรใส่ช่องไหน หรือดูตัวเลขในหน้า
dashboard แล้วไม่รู้ว่าหมายความว่าอะไร อ่านตารางนี้ก่อน

| ชื่อที่เห็นในระบบ | คืออะไร | หน่วย | มาจากไหน | ตัวเลขขึ้น แปลว่าอะไร |
| --- | --- | --- | --- | --- |
| **WCI** (Drewry World Container Index) | ค่าระวางเฉลี่ยของตู้คอนเทนเนอร์ขนาด 40 ฟุต จาก 8 เส้นทางเรือหลักทั่วโลก (เช่น เซี่ยงไฮ้–รอตเตอร์ดัม, เซี่ยงไฮ้–ลอสแอนเจลิส) เป็นดัชนีที่วงการพูดถึงกันบ่อยที่สุดตัวหนึ่ง | USD ต่อตู้ 40 ฟุต (FEU) | **กรอกมือทุกสัปดาห์** (ประกาศทุกวันพฤหัสบดี) — Drewry เผยแพร่เป็นกราฟบนเว็บ ไม่มีตารางให้ดึงอัตโนมัติ นี่คือทางหลักของดัชนีนี้ ไม่ใช่ทางสำรอง | ค่าระวางเรือแพงขึ้นจริง ต้นทุนส่งสินค้าทางเรือเพิ่มขึ้นตรงๆ |
| **SCFI** (Shanghai Containerized Freight Index) | คล้าย WCI แต่คำนวณจากราคาส่งออกจากท่าเรือจีน (เซี่ยงไฮ้) ไปเส้นทางหลักทั่วโลก เป็นตัวที่ตลาดเอเชียจับตามากที่สุด | **จุด (point)** ไม่ใช่ตัวเลขดอลลาร์ตรงๆ — ห้ามเอาไปเทียบตัวเลขตรงๆ กับ WCI ที่เป็น USD | ดึงอัตโนมัติทุกสัปดาห์จาก API ของ Shanghai Shipping Exchange เอง | จุดสูงขึ้น = ตลาดขาออกจากจีนตึงตัว เรือเต็มเร็ว ราคามีแนวโน้มขยับขึ้นตาม |
| **BDRY** | ไม่ใช่ค่าระวางตู้คอนเทนเนอร์ แต่เป็นกองทุน ETF ที่ซื้อขายในตลาดหุ้น ซึ่งราคาวิ่งตามค่าเช่าเรือสินค้าแห้งเทกอง (ถ่านหิน สินแร่ ธัญพืช) ใช้แทน Baltic Dry Index (BDI) ตัวจริงที่ Baltic Exchange ขายข้อมูลเชิงพาณิชย์ ไม่มีให้ดึงฟรีบน Yahoo Finance เลย | USD ต่อหน่วยกองทุน | ดึงอัตโนมัติทุกวันจาก Yahoo Finance | ราคาขึ้น = ความต้องการขนส่งสินค้าทางเรือ (ภาพรวมทั้งตลาด ไม่ใช่แค่ตู้คอนเทนเนอร์) กำลังแรงขึ้น เป็นสัญญาณทางอ้อม ใช้ประกอบการดูเทรนด์ ไม่ใช่ตัวเลขค่าระวางจริง |
| **WTI**, **Brent** | ราคาน้ำมันดิบล่วงหน้า (futures) — WTI คือเกณฑ์อ้างอิงของสหรัฐฯ, Brent คือเกณฑ์อ้างอิงสากล (ยุโรป/เอเชีย) | USD ต่อบาร์เรล | ดึงอัตโนมัติทุกวันจาก Yahoo Finance | น้ำมันแพงขึ้น = ต้นทุนน้ำมันเตาเรือ (bunker fuel) ของสายเรือสูงขึ้น ซึ่งสายเรือมักผลักภาระนี้มาเป็นค่าธรรมเนียมเพิ่ม (BAF / bunker surcharge) ให้ลูกค้าภายหลัง จึงเป็นสัญญาณล่วงหน้าของค่าระวางที่จะขึ้น |
| **ZIM** | ราคาหุ้นของ ZIM Integrated Shipping Services บริษัทสายเรือคอนเทนเนอร์ที่จดทะเบียนซื้อขายในตลาดหุ้นสหรัฐฯ | USD ต่อหุ้น | ดึงอัตโนมัติทุกวันจาก Yahoo Finance | หุ้นขึ้น = นักลงทุนมองว่าธุรกิจสายเรือกำลังทำกำไรดีขึ้น (เช่น ค่าระวางกำลังขึ้นหรือต้นทุนกำลังลง) เป็นสัญญาณความเชื่อมั่นของตลาดการเงินที่มีต่อธุรกิจสายเรือ ไม่ใช่ค่าระวางโดยตรง แต่มักขยับไปในทิศทางเดียวกัน |
| **VLSFO** | ราคาน้ำมันเตาเรือจริงที่สายเรือใช้เติม (ไม่ใช่ราคาน้ำมันดิบตั้งต้นแบบ WTI/Brent) เฉลี่ยจาก 20 ท่าเรือใหญ่ทั่วโลก | USD ต่อเมตริกตัน | ดึงอัตโนมัติทุกวันจาก Ship & Bunker | ราคาน้ำมันเตาแพงขึ้น = ต้นทุนที่สายเรือจ่ายจริงสูงขึ้นตรงๆ (ไม่ต้องผ่านการแปลงจากราคาน้ำมันดิบ) มักเป็นตัวที่สายเรือใช้อ้างอิงตั้งค่าธรรมเนียม BAF |

**สรุปสั้นๆ ให้จำง่าย:** มีแค่ **WCI** กับ **SCFI** เท่านั้นที่เป็น "ค่าระวางเรือ" จริงๆ
ที่เหลือ (BDRY, WTI, Brent, ZIM, VLSFO) เป็น **สัญญาณตลาดที่เกี่ยวข้อง** ใช้ประกอบการมองเทรนด์
ไม่ใช่ตัวเลขค่าระวางที่เอาไปเทียบกับใบเสนอราคาได้ตรงๆ — ตัวที่เทียบกับใบเสนอราคา
สายเรือได้โดยตรงในหน้า AHP คือ WCI/SCFI เท่านั้น ส่วน VLSFO คือตัวที่ตรงที่สุดในกลุ่มสัญญาณ
เพราะเป็นต้นทุนจริงที่สายเรือจ่าย ไม่ใช่ตัวแทนอย่าง WTI/Brent/ZIM

### เลขบาทที่ขึ้นใต้ตัวเลข USD คืออะไร

ตัวเลข "≈ xxx,xxx บาท" ที่ขึ้นใต้ดัชนีที่เป็นหน่วย USD (WCI, BDRY, WTI, Brent, ZIM)
เป็นการแปลงด้วยอัตราแลกเปลี่ยน USD→THB ปัจจุบัน ดึงจาก Frankfurter (อัตราอ้างอิงของ
ธนาคารกลางยุโรป ฟรี ไม่ต้องขอ API key) อัปเดตทุก 6 ชั่วโมง เพื่อให้เห็นตัวเลขเป็นบาท
โดยไม่ต้องแปลงเอง — **ใช้สำหรับดูภาพรวมเท่านั้น ไม่ใช่อัตราที่ธนาคารจะใช้คิดจริง**
ถ้าแปลงไม่ได้ (เน็ตล่ม หรือ Frankfurter ไม่ตอบ) ตัวเลขบาทจะไม่ขึ้น แต่ตัวเลข USD
หลักยังอยู่เหมือนเดิม — ไม่กระทบข้อมูลหลัก

### ตำแหน่งเรือ: ภาพรวม vs เรือเฉพาะลำ — คนละฟีเจอร์กัน

ระบบมี 2 ส่วนที่ดูเหมือนกันแต่ตอบคำถามคนละแบบ:

| | **ตำแหน่งเรือสด** (หน้าแรก) | **ติดตามเรือ** (`/admin/vessels`) |
| --- | --- | --- |
| ตอบคำถาม | "แถวนี้มีเรืออะไรบ้าง" | "เรือที่มีของเราอยู่ ตอนนี้อยู่ไหน" |
| ที่มา | ฝัง iframe จาก MarineTraffic | ต่อ aisstream.io เอง แล้วเก็บตำแหน่งลงฐานข้อมูล |
| วิธีดู | เปิดแผนที่ มีปุ่มสลับไปจุดคอขวดหลัก | กรอก MMSI ของเรือครั้งเดียว ระบบอัปเดตให้เองทุก 15 นาที |
| ความแม่นยำ | สดจริง (ของ MarineTraffic เอง) | ล่าสุดเท่าที่สัญญาณเรือมาถึงในรอบ 15 นาทีที่ผ่านมา ไม่ใช่สดเป๊ะ |

**ติดตามเรือ** คือฟีเจอร์ที่ต้องมี **MMSI** ของเรือ (เลข 9 หลัก ไม่ใช่ชื่อเรือ)
หาได้จากใบยืนยันการจองของสายเรือ หรือค้นชื่อเรือในแผนที่ตำแหน่งเรือสดที่หน้าแรกแล้วดู MMSI ที่นั่น
กรอกครั้งเดียวที่ `/admin/vessels` พร้อมเลือกท่าเรือปลายทาง (ถ้ารู้) ระบบจะคำนวณระยะทางที่เหลือ
และประมาณวันที่จะถึงให้ (จากความเร็วล่าสุดที่เรือรายงานมา — ถ้าเรือจอดนิ่งอยู่ จะไม่ประมาณวันให้
เพราะเอาความเร็ว 0 มาคำนวณแล้วตัวเลขจะมั่ว)

ทำไมไม่ใช้วิธีเดียวกับตำแหน่งเรือสด (ฝัง iframe): เพราะ iframe บอกได้แค่ "มีเรืออะไรแถวนี้"
ดูไม่ได้ว่าเรือลำไหนคือของเรา หรือคำนวณระยะทาง/วันที่จะถึงแบบที่ผูกกับท่าเรือปลายทางจริงของเราไม่ได้
ฟีเจอร์นี้จึงต่อ [aisstream.io](https://aisstream.io) ตรงๆ (บริการฟรี ให้ข้อมูล AIS แบบ WebSocket)
แล้วเก็บเฉพาะเรือที่เรากรอกไว้ลงฐานข้อมูลเอง — ต้องมี **`AISSTREAM_API_KEY`** ฟรีจากเว็บนั้นก่อนใช้งานได้
(สมัครด้วยอีเมล ไม่กี่ขั้นตอน) ถ้าไม่ตั้งค่าไว้ ส่วนอื่นของระบบทำงานปกติ มีแค่ job นี้ที่จะรายงานว่า
"ยังไม่ได้ตั้งค่า" แทนที่จะพังทั้งระบบ

aisstream.io ให้ข้อมูลผ่าน WebSocket เท่านั้น ไม่มี REST ให้ถามตรงๆ ว่า "เรือนี้อยู่ไหนตอนนี้"
ระบบจึงเปิดการเชื่อมต่อสั้นๆ (ฟังประมาณ 25 วินาที) ทุก 15 นาที แทนการเปิดค้างไว้ตลอด
(ซึ่ง Vercel serverless function ทำไม่ได้อยู่แล้ว) — เหมือนกับที่ข่าว RSS ใช้ GitHub Actions
แทน Vercel Cron เพราะ Hobby plan รัน cron ได้แค่วันละครั้ง ความถี่ 15 นาทีจึงมาจาก
`.github/workflows/track-vessels.yml` ไม่ใช่ `vercel.json` ต้องตั้ง repository secret
`APP_URL`/`CRON_SECRET` แบบเดียวกับ workflow ข่าว (ส่วน `AISSTREAM_API_KEY` ตั้งที่ฝั่ง Vercel
เท่านั้น ไม่ต้องใส่ใน GitHub เพราะ workflow นี้แค่เรียก endpoint ของเรา ไม่ได้คุยกับ aisstream.io ตรงๆ)

## ติดตั้ง

### 1. ติดตั้ง dependency

```bash
npm install
```

### 2. ตั้งค่า `.env`

คัดลอกจาก `.env.example` แล้วเติมค่าจาก Supabase

| ตัวแปร | เอามาจากไหน |
| --- | --- |
| `DATABASE_URL` | Supabase → Connect → **Transaction pooler** (พอร์ต 6543) |
| `DIRECT_URL` | Supabase → Connect → **Session pooler** (พอร์ต 5432) |
| `CRON_SECRET` | `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |

ทำไมต้องมีสองเส้น: migration รัน DDL ซึ่งผ่าน pgbouncer ไม่ได้ จึงต้องใช้ direct
connection ส่วนตัวแอปตอนรันใช้ pooler เพื่อไม่ให้ connection หมด

> ใช้ Session pooler เป็นค่าเริ่มต้นเพราะ direct connection (`db.<ref>.supabase.co`)
> เป็น IPv6 อย่างเดียว เครือข่ายที่ไม่มี IPv6 จะได้ error P1001
>
> รหัสผ่านที่มีอักขระสงวนของ URL เช่น `#` ต้อง encode ก่อน ไม่งั้นทุกอย่างหลังอักขระนั้นจะหายไป
> `node -e "console.log(encodeURIComponent('รหัสผ่าน'))"`

### 3. สร้างตารางและ seed

```bash
npm run db:migrate        # สร้างตารางตาม schema
npm run db:seed           # seed ท่าเรือ hub 6 แห่ง
npm run db:seed -- --demo # เพิ่มข้อมูลตัวอย่าง 26 สัปดาห์ สำหรับดู UI ก่อนมีข้อมูลจริง
```

### 4. สร้างบัญชีผู้ดูแลคนแรก

ระบบไม่มีการสมัครเอง บัญชีแรกต้องสร้างจาก CLI ไม่งั้นจะไม่มีใครเข้าหลังบ้านได้เลย

```bash
npm run user create napat ADMIN
```

คำสั่งจะถามรหัสผ่านแบบไม่แสดงบนหน้าจอ (ไม่รับรหัสผ่านเป็น argument เพราะจะไปค้างใน shell history และใน process list)

ข้อมูลตัวอย่างบันทึกเป็น `source=MANUAL` พร้อมหมายเหตุกำกับ ลบออกก่อนใช้งานจริงได้ง่าย

### 5. รัน

```bash
npm run dev
```

ตั้งไว้ใน `vercel.json` ทุก route ต้องส่ง `Authorization: Bearer $CRON_SECRET`

| Route | ตาราง | ทำอะไร |
| --- | --- | --- |
| `/api/cron/freight-index` | ศุกร์ 10:00 UTC | Scrape Drewry WCI และ SCFI |
| `/api/cron/market-sentiment` | ทุกวัน 06:00 UTC | ดึง BDRY, WTI, Brent, ZIM จาก Yahoo Finance (ตัด BDI ออก เพราะ Yahoo ไม่มีข้อมูลนี้เลย) และ VLSFO จาก Ship & Bunker — ดูความหมายแต่ละตัวที่ [ดัชนีและข้อมูลตลาดแต่ละตัวคืออะไร](#ดัชนีและข้อมูลตลาดแต่ละตัวคืออะไร) |
| `/api/cron/news` | ทุกวัน 07:00 UTC | อ่าน RSS จาก The Loadstar, gCaptain และ The Maritime Executive |
| `/api/cron/vessel-tracking` | ไม่ได้อยู่ใน `vercel.json` — ดูหัวข้อถัดไป | ฟังตำแหน่งเรือที่ติดตามไว้จาก aisstream.io สั้นๆ แล้วบันทึก |

### งานที่ต้องรันถี่กว่าวันละครั้ง บน Vercel Hobby

Vercel แพ็กเกจ Hobby จำกัด cron ไว้ที่วันละครั้ง ซึ่งช้าเกินไปสำหรับงาน 2 อย่าง:
ข่าวทะเลแดงที่ประกาศตอนบ่ายไม่ควรเพิ่งขึ้นหน้าจอตอนเช้าวันถัดไป และตำแหน่งเรือที่อัปเดต
วันละครั้งก็ไม่ต่างจากไม่มีตำแหน่งเลยสำหรับเรือที่กำลังเข้าใกล้ท่า

`.github/workflows/ingest-news.yml` (ทุก 4 ชั่วโมง) และ `.github/workflows/track-vessels.yml`
(ทุก 15 นาที) จึงยิง endpoint เดิมจาก GitHub Actions ซึ่งไม่มีข้อจำกัดนี้และไม่มีค่าใช้จ่าย
เปิดใช้โดยตั้ง repository secret สองตัวที่ Settings → Secrets and variables → Actions
(ใช้ร่วมกันทั้งสอง workflow)

| Secret | ค่า |
| --- | --- |
| `APP_URL` | URL ของ deployment เช่น `https://shippr.vercel.app` ไม่ต้องมี `/` ท้าย |
| `CRON_SECRET` | ค่าเดียวกับที่ตั้งใน Vercel environment |

เมื่อเปิด workflow ข่าวแล้ว **ให้ลบรายการ `/api/cron/news` ออกจาก `vercel.json`**
ไม่อย่างนั้นจะรันซ้อนกันวันละครั้ง (ไม่ทำให้ข้อมูลซ้ำ เพราะเป็น upsert แต่ทำให้ run log อ่านยาก)
ส่วนตำแหน่งเรือไม่ได้ใส่ไว้ใน `vercel.json` ตั้งแต่แรกเพราะวันละครั้งไม่มีประโยชน์เลยสำหรับงานนี้

ถ้าอัปเกรดเป็น Pro แล้ว ใช้ cron ของ Vercel อย่างเดียวได้ โดยเปลี่ยน schedule
ของ news กลับเป็น `0 */4 * * *` และเพิ่ม `/api/cron/vessel-tracking` ด้วย schedule ถี่ที่สุดที่ Pro รองรับ
แล้วปิดทั้งสอง workflow

ยิงเองเพื่อทดสอบ

```bash
curl -H "Authorization: Bearer $CRON_SECRET" http://localhost:3000/api/cron/news
```

รันซ้ำได้ไม่เกิดข้อมูลซ้ำ ทุกการเขียนเป็น upsert บน natural key

## เรื่องที่ควรรู้ก่อนแก้โค้ด

### ดัชนีที่ดึงอัตโนมัติไม่ได้จริงๆ ต้องกรอกมือ ไม่ใช่บั๊ก

Drewry แสดง WCI เป็นกราฟ ไม่มีตาราง HTML ให้ดึงตรงๆ — แต่หน้าเว็บมี
`<meta name="description">` ที่ auto-generate จากตัวเลขจริงของเขาเอง
(เช่น `"...World Container Index (WCI) fell 1% to $4,434 per 40ft container."`)
ระบบอ่านค่าจาก meta tag นี้เป็นทางหลัก เพราะนิ่งกว่าการ parse ข้อความบนหน้าเว็บที่เปลี่ยนคำได้ทุกสัปดาห์
ถ้า meta tag หายไปวันหนึ่ง จะ fallback ไปลองอ่านข้อความบนหน้าเว็บแทน
**กรอกมือยังเป็นทางสำรองสุดท้าย ไม่ใช่ทางหลักอีกต่อไป** แต่ยังสำคัญอยู่ เผื่อทั้งสองทางพังพร้อมกัน

Shanghai Shipping Exchange (SCFI) บล็อกบอทที่เรียกหน้าเว็บตรงๆ แต่มี JSON API
(`/currentIndex`) ที่หน้าเว็บเขาเองเรียกใช้และไม่ต้อง login ระบบเรียก API นี้ตรง
เร็วกว่าและนิ่งกว่าการ parse HTML มาก — ดูรายละเอียดที่ `src/lib/scraper-config.ts`

ถึงจะดึงได้แล้ว ทั้งสองแหล่งก็ยังเป็น "ผลข้างเคียง" ของการตั้งค่าเว็บของเขา ไม่ใช่ API
ที่เขาประกาศรองรับ จึงอาจเปลี่ยนรูปแบบโดยไม่แจ้งล่วงหน้าได้ทุกเมื่อ

เมื่อ scraper ล้มเหลวทั้งทางหลักและทางสำรอง ระบบจะ **ไม่เขียนอะไรเลย** และบันทึกไว้ใน `ScrapeRun`
หน้า dashboard จะขึ้นว่าข้อมูลค้าง เพราะการกินข้อมูลผิดเข้า benchmark ที่คนเอาไปตั้งราคา
แย่กว่าการไม่มีข้อมูล — ช่องว่างมองเห็นได้ แต่ตัวเลขผิดมองไม่เห็น

ทุก adapter validate ตัวเองด้วย Zod ก่อน return ค่าที่หลุดช่วงที่เป็นไปได้
(WCI 200–20,000 USD/FEU, SCFI 200–6,000 points, VLSFO 100–2,000 USD/MT)
ถือเป็นความล้มเหลวในการ parse

เวลาแหล่งข้อมูลเปลี่ยนหน้าเว็บ แก้ที่ `src/lib/scraper-config.ts` ที่เดียว

### เวลารอเทียบท่าไม่มี API ฟรีที่เชื่อถือได้

ข้อมูลส่วนนี้มาจากการกรอกมือหรือ import CSV รายสัปดาห์ที่ `/admin/ports`
ท่าเรือที่ยังไม่มีข้อมูลจะยังแสดงอยู่ในตาราง เพราะถ้าซ่อนไป คนที่กวาดตามองจะอ่านว่า
"ท่านี้ไม่แออัด"

### AHP คำนวณสองที่ แต่เชื่อที่เดียว

`src/lib/ahp.ts` เป็น pure function ที่รันทั้งบน browser (คำนวณสดตอนเลื่อน slider)
และบน server (ตอนบันทึก) **ผลที่บันทึกลงฐานข้อมูลคำนวณใหม่ที่ server เสมอ**
ถ้ารับผลจาก client มาเก็บ decision log จะใช้เป็นหลักฐานอ้างอิงไม่ได้

คะแนนสายเรือใช้ ideal-mode normalization จากตัวเลขในใบเสนอราคาจริง ไม่ใช่ pairwise matrix
อีก 5 ชุด เพราะนั่นจะกลายเป็นอีก 50 คำถามที่ไม่มีใครกรอกจบ และตัวเลขที่กรอก
(USD, วัน, on-time %) อยู่บน ratio scale จริงอยู่แล้ว

### `benchmarkSnapshot` ถูก freeze ไว้โดยตั้งใจ

decision memo ที่ลูกค้าเปิดอ่านอีก 6 สัปดาห์ต้องบอกว่าตลาด **ณ วันที่ตัดสินใจ** เป็นอย่างไร
ถ้าคำนวณสดจาก `FreightIndex` ทุกครั้ง ประวัติการตัดสินใจจะถูกเขียนทับเงียบๆ

### ทำไมถึงเขียน auth เอง

คำเตือน "อย่าเขียน auth เอง" หมายถึงส่วนที่พลาดง่ายและพลาดแล้วเจ็บ — OAuth,
การยืนยันอีเมล, ลิงก์รีเซ็ตรหัสผ่าน, การกู้บัญชี ซึ่งโปรเจกต์นี้ไม่มีสักอย่าง
ทีมมีไม่กี่คน admin สร้างบัญชีให้ ไม่มีสมัครเอง เหลือแค่ตรวจรหัสผ่านแล้วออก session

ที่ยึดไว้:

- **scrypt จาก `node:crypto`** พารามิเตอร์ตามเกณฑ์ OWASP (N=2^14) เก็บพารามิเตอร์ไว้ในสตริงแฮช
  เพื่อขึ้น cost ภายหลังได้โดยไม่ต้องให้ทุกคนตั้งรหัสใหม่ ไม่ต้องลง dependency และไม่มีปัญหา native build
- **ตอบช้าเท่ากัน** กรณีไม่มี username กับกรณีรหัสผิด ไม่งั้นเวลาตอบจะบอกได้ว่าชื่อไหนมีอยู่จริง
- **เก็บแค่ SHA-256 ของ session token** ใน DB ถ้าฐานข้อมูลหลุด token ที่หลุดไปใช้ต่อไม่ได้
- **session เป็นแถวในตาราง ไม่ใช่ JWT ที่เราเซ็นเอง** เพราะต้องเพิกถอนได้จริง
  เปลี่ยนรหัสผ่านเมื่อไหร่ session เก่าถูกลบทั้งหมด
- **ผิดเกิน 5 ครั้งล็อก 15 นาที** นับรายบัญชี

**ไม่มีรีเซ็ตรหัสผ่านด้วยตัวเอง** ลืมรหัสต้องให้ admin สั่ง
`npm run user passwd <ชื่อผู้ใช้>` นี่คือข้อแลกเปลี่ยนที่รับไว้โดยตั้งใจ
เพื่อไม่ต้องมีระบบส่งอีเมลและ reset token ซึ่งเป็นส่วนที่เขียนพลาดง่ายที่สุดของงาน auth

## Deploy ขึ้น Vercel

1. ต่อ repo กับ Vercel
2. ใส่ environment variable ให้ครบตามตารางข้างบน รวม `CRON_SECRET`
3. ตั้ง build command เป็น `prisma generate && next build` หรือเพิ่ม `postinstall` script
4. รัน `npm run db:deploy` กับฐานข้อมูล production
5. Cron ใน `vercel.json` จะเริ่มทำงานเอง (ต้องใช้แพ็กเกจที่รองรับ cron)
